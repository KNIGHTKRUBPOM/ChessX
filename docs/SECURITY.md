# ความปลอดภัยและความเป็นส่วนตัวของ ChessMess

เอกสารนี้อธิบายมาตรการในโค้ดและงานที่ต้องตั้งค่าบน staging/production ให้ตรวจผลจริงตาม [เช็กลิสต์ก่อนเปิดบริการ](PRODUCTION-CHECKLIST.md) และ [คู่มือตั้งค่า](MANUAL-SETUP.md)

## Threat model

| ความเสี่ยง | มาตรการในโค้ด | สิ่งที่ต้องตรวจและความเสี่ยงที่ยังเหลือ |
| --- | --- | --- |
| ยึดบัญชีด้วยรหัสผ่านรั่ว ลิงก์ปลอม หรือการผูก OAuth | ยืนยันอีเมล, OAuth PKCE, callback ตายตัว, ผูก provider โดยตรวจเจ้าของ session, TOTP และตรวจความสดของการยืนยันตัวตนสำหรับบางรายการ | ทดสอบการล็อกอินและการผูกบัญชีด้วย Google/Facebook บน staging รวมถึงอีเมลยังไม่ยืนยันและบัญชีอีเมลเดียวกัน ตรวจ redirect URL ตรงทุก environment และเปิด CAPTCHA กับการตรวจรหัสผ่านรั่วตามสิทธิ์แพ็กเกจ |
| ขโมย session หรือส่งคำสั่งจากเว็บอื่น | FastAPI ถือ token ผ่านคุกกี้ HttpOnly, SameSite=Lax และ Secure เมื่อใช้ HTTPS คำขอเขียนบัญชีตรวจ `Origin` ตาม `APP_ORIGIN` และส่ง `Cache-Control: no-store` | ตรวจคุกกี้และ header บนโดเมนจริง ทดสอบ logout ทุกอุปกรณ์ตามอายุ JWT การเพิกถอน refresh token ไม่ทำให้ access token ที่ออกไปแล้วหมดอายุทันทีทุกกรณี |
| เข้าถึงข้อมูลผู้เล่นอื่นหรือแก้สถิติเอง | RLS จำกัดเจ้าของแถวและบังคับ AAL2 เมื่อเปิด MFA สิทธิ์ UPDATE จำกัดคอลัมน์โปรไฟล์ ส่วนสถิติและผลเกมเขียนจากธุรกรรมฝั่งฐานข้อมูล | ทดสอบทั้ง FastAPI และ Data API โดยตรง สมมติว่า client สามารถเข้าถึง Supabase ด้วย publishable key ได้เสมอ ต้องทดสอบ AAL1/AAL2 แยกจากการทดสอบสิทธิ์เจ้าของแถว |
| โกงตาเดิน เปิดคำสั่งลับของคู่แข่ง หรือบันทึกผลซ้ำ | เซิร์ฟเวอร์ตรวจตาเดินและฝั่งของ seat token ส่ง snapshot เฉพาะที่ผู้เล่นคนนั้นเห็นได้ และป้องกันการเขียนชนกันด้วย revision ผลเกมใช้คีย์ `(match_id, player_id)` กันบันทึกซ้ำ | ผู้เล่นสองคนที่มีบัญชีจริงยังอาจนัดกันปั๊มสถิติ ตรวจพฤติกรรมก่อนใช้สถิติให้รางวัลหรือจัดอันดับ |
| บอตสมัครหรือสร้างห้องจำนวนมาก | มี CAPTCHA แบบ Turnstile เมื่อกำหนดค่าและจำกัดการสร้างห้องใน storage กลาง | ทดสอบเพดาน Auth บน staging ด้วยหลายไคลเอนต์ ตรวจว่า rate limit หลัง FastAPI กระทบผู้เล่นที่ใช้เครือข่ายร่วมกันอย่างไร และกำหนด alert สำหรับ 429/5xx และการส่งอีเมลผิดปกติ |
| Credential ฝั่งเซิร์ฟเวอร์หรือ CI รั่ว | แยกกุญแจสาธารณะและกุญแจเซิร์ฟเวอร์ แยก secrets ต่อ environment และมีงานตรวจ bundle, commit และ dependency | กุญแจเซิร์ฟเวอร์มีสิทธิ์ข้าม RLS จัดให้มีเจ้าของกุญแจที่ชัดเจนและจำกัดสิทธิ์ deploy แยกจากผู้รีวิว ตรวจ GitHub Environment และสิทธิ์ Dashboard ทุกครั้งที่เปลี่ยนทีม |

จุดอ้างอิงใน repo ได้แก่ [Auth และคุกกี้](../backend/account.py), [MFA, OAuth และข้อมูลบัญชี](../backend/account_security.py), [security headers](../backend/app.py), [สิทธิ์ฐานข้อมูลและธุรกรรมผลเกม](../supabase/migrations/20261116065846_account_profiles_history.sql) และ [การจัดเก็บห้อง](../backend/rooms.py) เอกสารผู้ให้บริการอธิบายข้อจำกัดของ session และการเชื่อม provider โดยละเอียด [Supabase Auth Sessions](https://supabase.com/docs/guides/auth/sessions) · [Supabase Identity Linking](https://supabase.com/docs/guides/auth/auth-identity-linking)

## ข้อมูลที่เก็บและการลบ

| ข้อมูล | ใช้ทำอะไรและใครเข้าถึง | ระยะเวลาและเงื่อนไข |
| --- | --- | --- |
| อีเมล, UUID, ข้อมูลยืนยันบัญชี, identity ของ provider, ข้อมูล MFA และ session | Supabase Auth ใช้ยืนยันตัวตน FastAPI ใช้ข้อมูลส่วนที่จำเป็นเพื่อให้บริการบัญชี | ข้อมูลบัญชีอยู่จนลบบัญชี Session และรหัสยืนยันหมดอายุตาม Auth settings |
| Username, ชื่อที่แสดง, URL รูปถ้ามี, เวลาสร้าง/แก้ไขและสถิติรวม | ให้เจ้าของจัดการโปรไฟล์และดูสถิติ ผู้เล่นในห้องเห็นชื่อที่ใช้เล่น | ตารางข้อมูลของผู้เล่นลบตามบัญชี สถิติสะสมคงอยู่ถึงวันลบบัญชี |
| ผลการแข่งขัน, ฝั่ง, โหมด, เวลาและรหัสแมตช์ | เจ้าของใช้ดูและส่งออกประวัติ เกมออนไลน์บันทึกเมื่อทั้งสองฝั่งเป็นบัญชีที่ตรวจสอบได้และเป็นคนละบัญชี | ตั้งเป้า 365 วัน หรือจนลบบัญชี ฟังก์ชันตัดข้อมูลต้องถูกเรียกตามตาราง |
| ห้องเกม, ชื่อที่ใช้ในห้อง, สถานะเกม, hash ของ seat token, การผูกที่นั่งกับบัญชี | ใช้กลับเข้าเกม ตรวจสิทธิ์ฝั่ง และบันทึกผล ห้องผูกรหัสบัญชีในตารางภายใน | ห้องรอหรือมีฝั่งออกอายุ 15 นาที ห้องที่เล่นอยู่ถึง 6 ชั่วโมงตามเวลาหมดอายุล่าสุด โค้ดปฏิเสธห้องที่หมดอายุและทำความสะอาดตามกลไกของ store ให้ตรวจการลบจริงแยกจากอายุสิทธิ์เข้าถึง |
| Account audit ได้แก่ ประเภทเหตุการณ์ เวลาและ UUID เมื่อจำเป็น | ตรวจสอบเหตุความปลอดภัยของบัญชี ข้อผิดพลาดล็อกอินใน audit ของแอปไม่มีตัวระบุผู้เล่น การลบบัญชีล้างตัวอ้างอิงผู้เล่นจาก audit เดิม | ตั้งเป้า 90 วัน ฟังก์ชันตัดข้อมูลต้องถูกเรียกตามตาราง ส่วน Vercel, Supabase และ SMTP ใช้ retention ตามแพ็กเกจที่ตั้งจริง |
| ธีมและเซฟเกมบนเครื่อง, ข้อมูลกลับเข้าที่นั่งของแท็บ | `localStorage` เก็บธีมและเซฟ `sessionStorage` ช่วยกลับเข้าที่นั่ง | เคลียร์เซฟของเว็บหรือล้าง site data เอง การลบบัญชีบนเซิร์ฟเวอร์มีผลกับข้อมูลฝั่งเซิร์ฟเวอร์ |
| สำเนาสำรอง, PITR และ log ในบริการภายนอก | กู้ระบบและสืบสวนเหตุ จำกัดผู้เข้าถึงตามหน้าที่ | ผู้ดูแลระบุช่วงเวลาและพื้นที่จัดเก็บจริงก่อนเปิดบริการ และทบทวนการจัดการคำขอลบหากมีการ restore |

- ตั้ง retention job ที่มีสิทธิ์เรียก `public.chessmess_prune_player_data()` ให้รันทุกวันผ่านช่องทางที่อนุมัติ ตรวจเวลารันล่าสุดและแจ้งเตือนเมื่อไม่สำเร็จ ทดสอบด้วย fixture หมดอายุใน staging ก่อนเปิด job ใน production [Supabase Cron](https://supabase.com/docs/guides/cron) · [Supabase Backups](https://supabase.com/docs/guides/platform/backups)
- การตั้งค่าบัญชีมีการดาวน์โหลด JSON แยกหน้าและลบบัญชี ให้เจ้าของติดต่อช่องทางในประกาศความเป็นส่วนตัวสำหรับคำขอนอกเหนือจากข้อมูลที่ self-service ส่งออกได้ ตรวจยืนยันตัวตนก่อนตอบและลงทะเบียนคำขอเท่าที่จำเป็น
- ผู้ควบคุมข้อมูลต้องกรอกผู้รับผิดชอบ วัตถุประสงค์ ฐานการประมวลผล ผู้รับข้อมูล การส่งข้อมูลไปต่างประเทศ ช่วงเวลาเก็บ log/backup และนโยบายเกี่ยวกับผู้เยาว์ตามการใช้งานจริง รวมถึงตรวจว่าระบบต้องมี DPO หรือหน้าที่เพิ่มเติมตามกฎหมายหรือไม่ เก็บสำเนาประกาศแต่ละฉบับและวันที่เริ่มใช้ [พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562](https://www.dol.go.th/PDPA/Documents/PDPA/PDPA-Act2019.pdf)
- หน้า [ประกาศความเป็นส่วนตัว](../public/privacy.html) และ [ข้อกำหนดการใช้งาน](../public/terms.html) เป็นร่างที่เจ้าของบริการต้องตรวจและกรอกให้ครบก่อนเผยแพร่

## กู้บัญชีเมื่อเสียอุปกรณ์ MFA

1. ขณะยังเข้าได้ ให้ลงทะเบียน TOTP ตัวสำรองแยกอุปกรณ์ ยืนยันรหัสตัวสำรองให้สำเร็จและลองเข้าสู่ระบบด้วยตัวสำรองก่อนเปลี่ยนเครื่อง เก็บ QR/seed ในที่ปลอดภัยและจำกัดผู้เข้าถึง
2. เมื่อเสียเครื่องหลัก ให้เข้าสู่ระบบด้วย factor ที่ยังอยู่ ยืนยันเป็น AAL2 แล้วลบ factor ของเครื่องที่หาย ตรวจรายการ provider และออกจากระบบทุกอุปกรณ์เมื่อสงสัยว่าเครื่องถูกขโมย
3. ลิงก์หรือรหัสกู้รหัสผ่านทางอีเมลช่วยตั้งรหัสผ่านใหม่ ผู้เล่นที่เปิด MFA ต้องผ่าน TOTP ที่ลงทะเบียนไว้จึงทำรายการกู้รหัสผ่านต่อได้
4. หากเสียทุก factor ให้ใช้ช่องทางสนับสนุนที่ระบุในหน้า Privacy เพื่อรายงานและรับคำแนะนำ ขณะนี้ไม่มี recovery codes หรือการปลด MFA อัตโนมัติสำหรับบัญชีผู้เล่น การเข้าถึงอีเมลเพียงอย่างเดียวยังยืนยัน AAL2 ไม่ได้ ให้ทีมสนับสนุนบันทึกคำร้องและรักษา MFA เดิมไว้เมื่อยืนยันสิทธิ์ไม่ได้ หากจะเพิ่มการกู้ผ่านเจ้าหน้าที่ในอนาคตให้มีหลักฐานยืนยันที่ลงทะเบียนไว้ล่วงหน้า ผู้อนุมัติอิสระสองคน การแจ้งเตือนเจ้าของบัญชี การเพิกถอน sessions และบันทึก audit ก่อนใช้งานจริง

ทดสอบกรณี factor สำรองและกรณี AAL1 ใน staging ก่อนเปิดให้สาธารณะ [Supabase Auth MFA](https://supabase.com/docs/guides/auth/auth-mfa) · [Supabase TOTP](https://supabase.com/docs/guides/auth/auth-mfa/totp)

## แจ้งเตือนและตอบสนองเหตุ

1. ตั้งผู้รับหลักและผู้รับสำรองสำหรับ Vercel 5xx, uptime/ความหน่วง, Supabase Auth failures/429, SMTP bounce/rate และความผิดปกติของการ deploy/การใช้ทรัพยากร กำหนด baseline จาก staging/ช่วงเปิดจริง ปิดการเก็บ body, คุกกี้, Authorization header, URL callback ที่มี auth code และข้อมูลส่วนบุคคลในระบบติดตาม error
2. เมื่อทราบเหตุ ให้เปิดบันทึกเหตุพร้อมเวลา UTC, environment, revision และตัวระบุคำขอจากแหล่งที่ตรวจสอบได้ เก็บหลักฐานในพื้นที่สิทธิ์จำกัด แยกจาก Git แล้วประเมินบัญชี บริการ และข้อมูลที่ได้รับผลกระทบ
3. จำกัดผลกระทบตามกรณี เช่น ระงับ provider ที่เกี่ยวข้อง พักฟีเจอร์บัญชีด้วย `CHESS_ACCOUNT_ENABLED=0` ผ่าน deploy ที่อนุมัติ หรือหยุด pipeline ที่ผิดปกติ ถ้า GitHub runner หรือ hosting token หลุด ให้เพิกถอนและสร้างใหม่จากบัญชีผู้ดูแลที่เชื่อถือได้
4. หมุน credential ที่ได้รับผลกระทบเฉพาะ environment นั้น อัปเดต GitHub Environment, Vercel หรือ Supabase Dashboard ตามที่เก็บจริง แล้วตรวจ smoke ก่อนยกเลิก credential เก่า หากยืนยันว่ารั่ว ให้เพิกถอนทันทีและใช้ขั้นตอนกู้บริการ สำหรับ signing key ให้ตรวจผลกับ session และประสานการเพิกถอนก่อนตัดรุ่นเก่า [Supabase JWT Signing Keys](https://supabase.com/docs/guides/auth/signing-keys)
5. ประเมินหน้าที่แจ้งเหตุข้อมูลส่วนบุคคลกับผู้รับผิดชอบ เมื่อเข้าหลักเกณฑ์มาตรา 37(4) ให้แจ้ง สคส. โดยไม่ชักช้า ภายใน 72 ชั่วโมงนับแต่ทราบเหตุเท่าที่ทำได้ หากมีความเสี่ยงสูงให้แจ้งเจ้าของข้อมูลพร้อมแนวทางเยียวยาโดยไม่ชักช้าตามหลักเกณฑ์ [มาตรา 37(4) ในฉบับราชกิจจานุเบกษา](https://www.dol.go.th/PDPA/Documents/PDPA/PDPA-Act2019.pdf)
6. ยืนยันการกู้จากสภาพแวดล้อมแยกก่อนเปิดรับการเขียน คืน deployment หรือใช้ forward-fix ตาม [CICD](CICD.md) ตรวจว่าข้อมูลที่เคยลบไม่ถูกนำกลับมาเปิดเผยหลัง restore แล้วเพิ่ม regression test และงานแก้รากเหตุ

กำหนดวันตรวจรายการ credential อย่างน้อยทุกไตรมาสและทุกครั้งเมื่อสมาชิกทีมออก โดยใช้สิทธิ์ต่ำสุดสำหรับ GitHub, Vercel, Supabase และ OAuth dashboard [Supabase Production Security Checklist](https://supabase.com/docs/guides/security/production-checklist)
